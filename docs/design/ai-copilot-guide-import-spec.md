# AI 攻略导入与作业生成规范

## 1. 背景

MaaYuan 已经具备完整的模拟器控制、图像识别、回合检测、战斗动作执行、失败重开和作业导入能力。当前“抄作业”链路的主要使用成本不在执行阶段，而在于：

1. 玩家需要从图片、帖子或视频中理解攻略；
2. 玩家需要把攻略逐回合手工录入作业编辑器；
3. 攻略作者使用的符号、缩写和条件描述不统一；
4. 复杂关卡存在阶段切换、目标切换、条件分支、循环和随机事件，容易录错；
5. 作业文件格式面向执行器，不适合作为大模型直接生成的第一层输出。

本功能在现有 MaaYuan “抄作业”系统上增加一层 **AI 攻略导入器**，将攻略截图或文字转换成经过用户确认、静态校验并可直接运行的 MaaYuan 作业。

## 2. 目标

### 2.1 核心目标

用户提供一份攻略截图或攻略文字后，系统应能够：

1. 识别阵容、站位、回合表格、动作符号、目标和备注；
2. 生成统一的中间表示，而不是直接生成 MaaYuan pipeline JSON；
3. 标记有歧义或低置信度的解析结果；
4. 允许用户在类表格界面中确认和修正；
5. 对作业执行逻辑进行静态校验；
6. 编译为 MaaYuan 当前支持的作业格式；
7. 复用现有抄作业执行链路完成自动战斗。

### 2.2 非目标

首期不实现：

- AI 在完全没有攻略的情况下自主求解关卡；
- 基于完整战斗模拟器搜索最优阵容；
- 自动识别全部密探技能、命盘、星石和伤害公式；
- 自动修复所有运行时失败；
- 无人工确认地直接执行低置信度攻略；
- 对任意模拟器分辨率做通用视觉适配。

## 3. 用户流程

### 3.1 标准流程

1. 用户进入“抄作业”页面；
2. 选择“AI 导入攻略”；
3. 上传一张或多张攻略图片，或粘贴攻略文字；
4. 选择游戏版本、关卡、阵容和站位；
5. 系统执行 OCR/VLM 解析；
6. 系统展示：
   - 原始攻略；
   - 解析后的回合表；
   - 全局规则；
   - 阶段规则；
   - 低置信度项；
7. 用户确认或修改歧义项；
8. 系统执行静态校验；
9. 用户预览生成的 MaaYuan 作业；
10. 用户保存到本地或导入现有作业编辑器；
11. MaaYuan 使用现有抄作业执行器运行作业。

### 3.2 快速流程

对于规则简单、置信度高的攻略：

1. 上传图片；
2. 确认阵容；
3. 系统自动解析并校验；
4. 用户点击“一键生成作业”。

### 3.3 运行失败后的反馈流程

运行失败时，应保存：

- 作业 ID 和版本；
- 失败回合；
- 最近若干动作；
- 当前屏幕截图；
- 识别结果；
- 执行器日志；
- 失败类型。

后续版本可用这些信息生成“建议修正”，但首期只要求导出诊断包。

## 4. 输入类型

### 4.1 图片

支持：

- 单张回合表；
- 多张连续攻略图；
- 带阵容头像和备注的表格截图；
- 纯文字截图。

建议限制：

- PNG、JPEG、WebP；
- 单文件不超过 20 MB；
- 最多 10 张；
- 至少一边大于 800 px。

### 4.2 文字

支持：

- 纯文本；
- Markdown；
- 从小红书、微博、B 站简介等复制的文字；
- 用户手动输入的自然语言攻略。

### 4.3 视频

首期不直接解析视频。用户可上传字幕、文字稿或关键帧截图。视频逐帧识别作为后续扩展。

## 5. 术语与动作模型

### 5.1 基础动作

统一动作枚举：

```text
attack          普攻
ultimate        上拉释放大招
defend          下拉防御
switch_state    点击圆圈切换状态
select_ally     选择我方目标
select_enemy    选择敌方目标
wait            等待
pause           暂停并请求人工接管
restart         重开
```

### 5.2 条件动作

条件动作不直接成为底层执行动作，而是在编译阶段展开：

```text
ultimate_if_ready_else_attack
ultimate_if_ready_else_defend
attack_if_safe_else_defend
switch_state_if_available
```

### 5.3 常见攻略符号

系统应内置可编辑的符号词典：

| 原始符号 | 默认解释 |
|---|---|
| A、a、普 | 普攻 |
| ↑、上、开大 | 大招 |
| ↓、防 | 防御 |
| ○、圈、点圈 | 切换状态 |
| A/↑ | 有大开大，否则普攻 |
| A/↓ | 普攻或按条件防御，必须确认条件 |
| 1-5 | 我方站位 |
| 6-10 | 敌方站位或作者自定义编号，必须结合上下文确认 |

系统不得把未知缩写强行解释为确定动作。低于阈值的项必须进入确认列表。

## 6. 中间表示 IR

### 6.1 设计原则

AI 输出必须先转换为独立于 MaaYuan pipeline 的中间表示，原因如下：

- 易于人工阅读；
- 易于进行 schema 校验；
- 易于做版本迁移；
- MaaYuan 作业格式变化时只需要修改 compiler；
- 避免模型直接生成大段脆弱的 pipeline JSON；
- 支持未来接入不同模型和解析器。

### 6.2 顶层结构

```yaml
schema_version: 1
metadata:
  title: string
  game_variant: code_name_yuan | ru_yuan
  stage: string
  source_type: image | text | mixed
  source_notes: string | null
  author: string | null

party:
  - slot: 1
    operator: 卢植
    aliases: []
    optional: false

symbols:
  A: attack
  "↑": ultimate
  "↓": defend

phases: []
global_rules: []
turn_plans: []
validation_overrides: []
```

### 6.3 阵容结构

```yaml
party:
  - slot: 1
    operator: 卢植
    variant: null
    optional: false
    requirements:
      level: null
      star: null
      hp_min: null
      attack_min: null
      astrology: []
```

首期只强制要求 `slot` 和 `operator`。其余用于筛选、展示和未来校验。

### 6.4 回合计划

```yaml
turn_plans:
  - phase: phase_1
    turn: 1
    repeat_group: null
    target:
      type: enemy_slot
      value: 2
    actions:
      - sequence: 1
        actor_slot: 1
        action: attack
      - sequence: 2
        actor_slot: 2
        action: ultimate_if_ready_else_attack
```

动作顺序必须显式保存，不能只把五个角色动作存成无序字典。

### 6.5 阶段

```yaml
phases:
  - id: phase_1
    name: 一命
    enter_when:
      type: battle_start
    exit_when:
      type: enemy_phase_changed
      enemy_slot: 2

  - id: phase_2
    name: 二命
    enter_when:
      type: enemy_phase
      enemy_slot: 2
      phase: 2
```

### 6.6 规则

```yaml
global_rules:
  - id: boss_ult_target
    priority: 100
    when:
      all:
        - type: enemy_ultimate_ready
          enemy_slot: 2
    then:
      - action: select_ally
        ally_slot: 5

  - id: defend_after_healer_ult
    priority: 80
    when:
      all:
        - type: last_action
          actor_slot: 3
          action: ultimate
    then:
      - action: override_next_actor
        next_action: defend
```

### 6.7 循环

```yaml
turn_plans:
  - phase: phase_1
    repeat_group: loop_1_2
    turn: 1
    actions: []
  - phase: phase_1
    repeat_group: loop_1_2
    turn: 2
    actions: []

repeat_groups:
  - id: loop_1_2
    sequence: [1, 2]
    until:
      type: phase_exit
      phase: phase_1
    max_iterations: 10
```

所有循环必须有：

- 明确终止条件；
- 最大迭代次数；
- 失败时策略。

## 7. AI 解析流程

### 7.1 分层解析

解析分为四步：

1. **版面检测**：识别表格、头像、回合列、动作格、备注区；
2. **文字与符号提取**：OCR 提取文本，VLM 补充复杂布局理解；
3. **语义归一化**：转换为统一动作、条件、阶段和目标；
4. **IR 生成**：输出符合 schema 的中间表示。

### 7.2 模型职责

模型负责：

- 理解非标准表格；
- 识别自然语言条件；
- 推断备注与具体回合的关联；
- 识别可能的阶段切换；
- 为每个字段提供置信度和证据区域。

模型不负责：

- 直接执行模拟器动作；
- 绕过 schema 生成任意 pipeline；
- 在低置信度时自行作出不可逆决定；
- 假定未知缩写的含义。

### 7.3 解析结果格式

AI 返回：

```json
{
  "ir": {},
  "uncertainties": [
    {
      "id": "u-1",
      "source": "A/↓",
      "location": "turn 2, slot 3",
      "candidates": [
        "attack_if_safe_else_defend",
        "attack_then_defend"
      ],
      "recommended": "attack_if_safe_else_defend",
      "confidence": 0.58,
      "reason": "攻略未给出防御触发条件"
    }
  ],
  "warnings": [],
  "evidence": []
}
```

## 8. 置信度与人工确认

### 8.1 阈值

建议默认阈值：

- `>= 0.90`：自动接受；
- `0.70 - 0.89`：展示提醒，可批量接受；
- `< 0.70`：强制确认；
- 影响阶段、目标、循环或动作顺序的字段，即使置信度较高也应重点展示。

### 8.2 必须确认的情况

以下情况必须人工确认：

- 未知符号；
- 同一符号在不同位置被解释成不同动作；
- 空白格语义不明；
- 编号可能同时代表站位、火数或技能序号；
- “下一位”“第二个行动者”等相对顺序描述；
- 目标名称无法唯一对应敌方位置；
- 阶段终止条件缺失；
- 攻略中存在互相冲突的描述。

## 9. 静态校验

### 9.1 错误级别

- `ERROR`：禁止生成作业；
- `WARNING`：允许生成，但必须展示；
- `INFO`：提示用户注意。

### 9.2 必须实现的校验

1. 站位必须在 1-5；
2. 同一回合同一角色不能执行两次主动作，除非动作模型明确支持；
3. 动作顺序不能重复；
4. 所有引用的角色必须存在；
5. 所有阶段必须可进入；
6. 所有循环必须有终止条件和最大次数；
7. 条件动作必须有 fallback；
8. 目标切换必须指向可识别的目标；
9. “下一位防御”不得越过回合边界，除非显式允许；
10. 作业必须至少有一个终止路径；
11. 未解决的强制确认项必须为零；
12. 编译后的 pipeline 节点名不能冲突。

### 9.3 可选校验

- 每回合是否覆盖全部存活角色；
- 攻略预计结束回合是否合理；
- 是否存在永远无法触发的规则；
- 高优先级规则是否覆盖普通回合计划；
- 队伍属性是否满足攻略要求。

## 10. Compiler

### 10.1 职责

Compiler 将 IR 转换为 MaaYuan 当前作业格式，并复用已有节点：

- 回合检测；
- 站位普攻；
- 站位上拉；
- 站位下拉；
- 点击状态圈；
- 目标选择；
- 胜利识别；
- 全灭重开；
- 暂停提醒。

### 10.2 编译要求

- 输出必须稳定且可重复；
- 相同 IR 应生成语义等价的作业；
- 节点命名包含作业前缀，避免与系统节点冲突；
- 所有生成节点必须可追溯到 IR 中的 source ID；
- 生成结果必须通过 JSON/schema 校验；
- 禁止覆盖系统内置 pipeline 文件；
- 生成文件保存到用户作业目录。

### 10.3 兼容策略

IR 中必须保存：

```yaml
schema_version: 1
compiler_target:
  min_maayuan_version: null
  pipeline_format_version: 1
```

当 MaaYuan 作业格式变化时：

- 保留旧 IR；
- 增加新的 compiler target；
- 不要求重新解析原攻略。

## 11. UI 规范

### 11.1 导入页面

页面包含：

- 文件上传区；
- 文字粘贴区；
- 游戏版本；
- 关卡名称；
- 阵容和站位选择；
- 模型配置；
- “开始解析”按钮。

### 11.2 确认页面

推荐三栏布局：

1. 左侧：原图或原文；
2. 中间：回合表格和规则；
3. 右侧：歧义项、错误、警告和字段详情。

用户点击某个动作单元格时，原图定位到对应证据区域。

### 11.3 回合表编辑

表格至少包含：

- 阶段；
- 回合；
- 目标；
- 1-5 号位动作；
- 动作顺序；
- 回合备注；
- 置信度；
- 校验状态。

### 11.4 生成页面

展示：

- 校验摘要；
- 作业元数据；
- 生成节点数；
- 未覆盖规则；
- JSON 预览；
- 保存、导入、复制和下载按钮。

## 12. 数据与隐私

- 默认不永久保存用户上传的攻略图片；
- 若使用远程模型，应明确告知图片会发送到第三方服务；
- API Key 只保存在本地安全存储，不写入日志；
- 日志中不得记录完整 API Key；
- 用户可选择本地模型或关闭 AI 功能；
- 导出的诊断包默认去除账号信息。

## 13. 错误处理

### 13.1 解析失败

系统应保留已识别部分，并允许用户：

- 重试；
- 更换模型；
- 手动补录；
- 只导入已确认的回合。

### 13.2 编译失败

展示：

- 错误节点；
- 对应 IR 路径；
- 原始证据；
- 建议修改项。

### 13.3 执行失败

执行器行为保持现有抄作业逻辑。AI 模块只增加诊断信息，不改变默认安全策略。

## 14. 可观测性

记录以下指标：

- 解析耗时；
- OCR/VLM 调用次数；
- 每个字段置信度；
- 用户修改次数；
- 静态校验错误数；
- 首次编译成功率；
- 首次运行成功率；
- 失败回合分布；
- 不同模型的解析准确率和成本。

不得上传用户攻略内容作为遥测，除非用户明确选择加入改进计划。

## 15. 测试策略

### 15.1 单元测试

- 符号归一化；
- IR schema；
- 条件表达式；
- 循环展开；
- 节点命名；
- compiler 输出；
- 校验器规则。

### 15.2 Golden tests

建立人工标注测试集：

```text
tests/fixtures/ai_copilot/
  simple_table/
  multi_phase/
  ambiguous_symbols/
  target_switch/
  repeated_turns/
  text_only/
```

每个 fixture 包含：

- 原图或原文；
- 期望 OCR；
- 期望 IR；
- 期望歧义列表；
- 期望编译结果摘要。

### 15.3 集成测试

在固定 `1280x720, 320dpi` 的模拟器环境中验证：

- 作业可加载；
- 回合检测正确；
- 五种基础动作正确；
- 阶段切换正确；
- 全灭重开正确；
- 暂停保护正确。

### 15.4 评测指标

- 单元格动作准确率；
- 动作顺序准确率；
- 目标识别准确率；
- 阶段规则准确率；
- 强制确认召回率；
- 错误自动接受率；
- 用户平均修改次数；
- 首次作业运行成功率。

重点控制 **错误自动接受率**，而不是只追求高自动填充率。

## 16. 安全与停止条件

生成作业必须继承现有执行器保护，并增加：

- 未知界面暂停；
- 当前回合与预期不一致时暂停；
- 目标无法确认时暂停；
- 连续动作无画面变化时暂停；
- 循环达到最大次数时暂停；
- 意外阵亡时按作业策略重开或暂停；
- 用户可配置全局紧急停止快捷键。

## 17. 验收标准

MVP 完成标准：

1. 支持上传一张标准回合表截图；
2. 能识别阵容、回合和基础动作；
3. 能生成 IR；
4. 能展示并修改歧义项；
5. 能执行静态校验；
6. 能编译成 MaaYuan 可导入作业；
7. 至少有 10 份人工标注攻略 fixture；
8. 对无歧义基础动作的单元格识别准确率达到 95%；
9. 低置信度和未知符号不会被静默自动接受；
10. 生成作业能够复用现有抄作业执行链路完成至少一个真实关卡。

## 18. 后续扩展

- 视频关键帧和字幕解析；
- 作业站直接上传攻略图生成草稿；
- 用户纠正结果反哺个人符号词典；
- 运行失败截图自动定位到原攻略规则；
- 多模型评审；
- 基于已有作业召回相似模板；
- AI 辅助修复，而不是直接自主决策；
- 未知关卡的有限搜索和策略建议。
